# Grok 1.5 数字人口播提示词与素材输入指南

资料核对日期：2026-08-24。官方能力来自 xAI 文档；当前默认视频服务商为 91topgo，MikuAPI 仅在提交前显式降级。下文有关 Files API、预设声音和多参考图开关的限制专指 MikuAPI，不能直接推断 91topgo 也支持这些字段。

## 1. 先选对生成模式

| 模式 | 输入 | 最适合 | 关键限制 |
| --- | --- | --- | --- |
| `image-to-video` | 一张首帧图 `image` | 固定构图、固定开场姿态的口播 | 参考图就是第一帧，不能再传 `reference_images` |
| `reference-to-video` | 1-7 张 `reference_images`，可选最多 3 个预设声音 | 人物、服装、产品、场景分别锁定 | 不锁定第一帧，最高 720p，不能和 `image` 或视频编辑混用 |

数字人口播的多参考图模式即使官方允许“只有声音”，本 Skill 仍要求至少一张 `identity` 图。原因很简单：没有身份图就无法建立可检查的人物一致性合同。

## 2. 参考图不是越多越好

每张图只承担一个主要职责，按请求顺序记录：

- `identity`：脸型、发型、年龄感、身体特征；必须至少一张。
- `wardrobe`：服装款式、颜色、材质。
- `product`：产品外观、结构、颜色、比例。
- `scene`：空间布局和背景环境。
- `style`：摄影质感、色调、光影。
- `composition`：景别、构图、机位关系。

选择规则：能用 2-4 张解决时不要凑满 7 张；同一职责出现互相冲突的图片时先停止；低清、遮脸、强滤镜、多人合照或带大面积文字的图不进入生产请求。

官方 REST 示例用 `<IMAGE_1>`、`<IMAGE_2>` 指向列表中的参考图，但同页说明文字也出现 `<IMAGE_0>` 的写法。当前 Skill 把起始编号放在配置项 `reference_image_prompt_index_base`，默认按可运行示例使用 1；中转站验收若证明编号不同，只改配置和测试，不改提示词业务结构。

## 3. 音频能力要分成两类

- **预设声音**：官方普遍开放，通过 `reference_audios: [{"voice_id": "eve"}]` 使用，最多 3 个；提示词用 `<AUDIO_0>`、`<AUDIO_1>`、`<AUDIO_2>` 指向声音。
- **用户自己的音频文件**：官方明确写为“可信合作方申请开放”。没有 xAI 权限证明和 MikuAPI 透传验收时，只能用于内容分析、语速参考和本地质检，不能上传到视频接口，也不能承诺保留原音色。

当前 MikuAPI 的 `/v1/files` 已实测返回 HTTP 404，因此本 Skill 默认不引用外部声音：在没有预设 `voice_id` 时，提示词会明确写入“由模型生成口播人声”。`voice_profile` 必须是 8 项结构化字段：性别听感、年龄感、音高、音色、语速、情绪、发音和口音。它们会生成 `voice_signature`，同一项目的每段必须完全一致。

`voice_signature` 只是工程上的“防误改指纹”：它能发现某一段的声音描述被改了，但不能保证模型真正生成相同音色。声音身份保持一致，句子间允许自然的语调、语速和情绪变化；不能把“音色一致”误写为“整段音高、语速、情绪完全不变”。稳定做法是同时复用同一张人物主参考图和同一组声音字段，生成后再逐段实听。

2026-08-24 的一次授权短片证明这条默认路线在 MikuAPI 可用：1 秒、480p、16:9 单图请求只提交一次且未发送用户 MP3；成片包含 AAC 人声和可见口型，本地 Whisper 准确识别台词“你好”。该结果不能外推为原声复刻、长句准确率或跨段声音一致性。

数字人口播默认只有一个说话人，因此即使接口最多支持 3 个预设声音，也通常只传一个 `<AUDIO_0>`。多声音必须在方案中逐个对应说话主体，禁止让模型自行猜测。

## 4. 专业提示词结构

不要写一大段堆满形容词的“文学提示词”。每段按固定顺序生成：

1. **参考素材分工**：逐一写明 `<IMAGE_n>` 只控制什么；禁止职责互换。
2. **声音映射**：需要时写 `<AUDIO_0>` 对应哪个说话人。
3. **连续性锁定**：人物、服装、场景、机位、灯光、动作范围。
4. **视觉质感**：真实摄影、皮肤纹理、色彩和光线。
5. **镜头设计**：景别、机位、镜头是否固定或轻微运动；一段只保留一个主镜头意图。
6. **人物表演**：视线、表情、眨眼、呼吸、点头和克制手势。
7. **完整台词**：语言、逐字台词和语气。提示词可以要求准确说出，但最终仍必须听写验收，不能仅凭请求文本宣称“台词准确”。
8. **声音设计**：环境声、是否有音乐、人声优先级。
9. **时间节奏**：起始稳定、台词过程、句尾收声；不在句中切镜。
10. **强制限制**：无字幕、文字、标题、Logo、水印、UI；无换脸、重复人物、畸变、闪烁或冲突声音。

`speech_rate_cpm` 记录计划语速，默认每分钟 260 个汉字，分段估时直接使用同一数值。`performance_beats` 按 `segment_index` 指向片段；每项必须有该段台词中实际出现的 `trigger_phrase` 和对应 `expression`，`gesture` 可选。新视频运行 `prepare --video-prompt-spec <JSON>`，默认强制每段至少一个语义明确的节拍。15 秒片段通常只安排一处主手势；其他节拍可只改变表情，不要把静态手部姿势伪装成动作。模板中的示例短语必须在 `prepare` 前替换，否则分段校验会停止。提示词生成器会把动作写在本段台词后，要求轻微发生并自然回位。`speech_delivery` 只写自然语速、准确发音、语义停顿，不能写“前3秒/中间9秒/最后3秒”的固定口播时间格。`prepare` 对新项目会拦截这种冲突；写稿时先用 `plan` 检查用户目标与内容是否匹配，再按真实分段设计表演。时长决策与改稿规则见 `duration-planning.md`。

可调内容统一写进 `assets/video-prompt-spec-template.json`，新制作版本为 `3.0`（保留旧 `2.0` 合同读取），由 `scripts/video_prompt.py` 验证并生成最终提示词。这样每次修改都有版本、有字符上限，也能在付费前被测试和锁定。

## 5. 文件上传方案

官方图片输入支持公共 HTTPS、Base64 和 Files API `file_id`。本 Skill 只实现两条可审计路线：

- `public-https`：私密文件只记录在权限 600 的 `provider-inputs.json` 中，合同里只写摘要。
- `provider-file`：代码保留的可选路线；当前 MikuAPI 实测 `/v1/files` 返回 404，配置会阻止生产运行。

Files API 安全规则：单文件上限采用官方指南中更保守的 48MB；默认 24 小时自动过期；允许范围 1 小时至 30 天；multipart 中 `expires_after` 必须出现在 `file` 前；上传账本和 `file_id` 使用 600 权限。当前实现不上传音频。

## 6. MikuAPI 上线门槛

当前 MikuAPI 已验证 4 秒、480p、9:16 和 15 秒、480p、16:9 的单图 `image` 请求；15 秒单段成功不代表长句逐字准确或跨段连续性已经通过。以下能力虽然代码和离线测试已准备好，但配置默认关闭：

- `reference_images` 多参考图透传；
- `reference_audios` 预设声音透传；
- `/v1/files` 上传和 `file_id` 输入（已实测 HTTP 404）；
- 1080p；
- 用户自己的音频文件参考。

每项必须单独做“最小、一次、明确授权”的验收；失败或结果不明不自动重试。不能用官方文档、离线模拟测试或模型列表可见性替代中转站真实兼容性证据。

必读 `voice-casting-and-text-review.md`。3.0 增加必填角色选角，模板占位符必须替换。固定声音锚点逐段复用，出图后核对，首段实听验收；无文字画面规则由程序追加，不能被自定义负面提示词列表覆盖。最终验收不能只看开头、中间与九成时长的画面，必须包括真实最后一帧及全片检查。
